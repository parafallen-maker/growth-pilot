# 18 分支与提交规范

> 用途：给多 Agent 同仓协作时统一分支、提交、合并、交接和避冲突规则。
> 核心目标：减少互踩、减少返工、减少“看起来都在做，实际上谁也没接住”的混乱。

---

## 1. 基本原则

1. `main` 是**总分支 / 真正集成分支**。
2. 多 Agent 不直接长期共用一个工作副本瞎改；要按任务卡切短分支。
3. 任务以 `16_多Agent派工清单.yaml` 为准，分支命名必须能回溯到 `agent + task_id`。
4. 小步提交、频繁回收，不堆超大脏分支。
5. 所有交付必须能回答三件事：
   - 你改了什么
   - 你为什么改
   - 你准备交给谁接下一棒

---

## 2. 总分支策略

## 2.1 `main` 的定位
- `main` 永远代表当前团队认可的最新集成状态
- 可以不等到“完美”才进 `main`，但必须保证：
  - 能通过最基本 lint / typecheck
  - 不破坏已通过的主流程
  - 有明确的提交说明

## 2.2 `main` 上不允许的事
- 不允许把未验证的大坨实验代码直接砸进 `main`
- 不允许跨模块胡改并且没有 handoff 说明
- 不允许字段改名但不更新 OpenAPI / DDL / 页面使用方
- 不允许为赶进度绕过测试又不留风险说明

---

## 3. 分支命名规范

### 3.1 Agent 任务分支

格式：

```text
agent/<agent-id>/<task-id>
```

例子：

```text
agent/A4/T-P0-2
agent/A5/T-M1-2
agent/A6/T-H1-3
agent/A9/T-B1-FE
```

### 3.2 集成分支（可选）

当一整波任务需要先合流再进 `main`，可使用：

```text
int/<wave>
```

例子：

```text
int/wave-2
int/wave-3
```

### 3.3 热修复分支

```text
hotfix/<module>/<short-name>
```

例子：

```text
hotfix/auth/token-refresh-loop
hotfix/billing/payment-status-bug
```

---

## 4. 提交规范

### 4.1 Commit message 规则

建议格式：

```text
<type>(<scope>): <summary>
```

常用类型：
- `feat`：新增功能
- `fix`：修复缺陷
- `refactor`：重构
- `docs`：文档
- `test`：测试
- `chore`：工程配置、依赖、脚本

例子：

```text
feat(students): add student profile and enrollment APIs
feat(homework): add AI job queue and review transaction
docs(growthpilot): add multi-agent dispatch cards
fix(billing): correct invoice payment status transition
chore(monorepo): setup pnpm workspace and CI
```

### 4.2 提交粒度
- 一个 commit 尽量只做一件事
- 不把“重命名 + 新功能 + 修 bug + 格式化全仓”混在同一个 commit
- 文档改动与代码改动若强耦合，可一起提交；否则分开更清楚

### 4.3 必带信息
如果是关键模块提交，正文建议补：

```text
WBS: WBS-019,WBS-020
Task: T-H1-1,T-H1-2
Handoff: A9,A10
```

---

## 5. 默认协作模式：任务文件是可执行的，不是摆设

这是本项目的硬规则。

### 5.1 默认解释
- `task` / `todo` / `dispatch` / `checklist` 类文件一旦进入仓库，默认视为**待执行清单**。
- Agent 对仓库内部交付事项默认**自动推进**，不逐条再问一遍“要不要开始”“要不要继续”。
- 做完后需要回写状态、交接记录、提交记录，而不是嘴上说完成。

### 5.2 允许自动执行的范围
以下内容默认自动执行：
- 仓库内代码实现
- 文档补全与更新
- 测试、联调、回归
- 脚手架、CI、类型生成、代码规范
- 数据迁移脚本与测试数据准备
- 页面骨架、接口联调、聚合查询、验收清单维护

### 5.3 必须暂停并询问的范围
只有这些情况才需要停下来问：
1. 对外发送消息、邮件、公告、PR 评论等外部动作
2. 不可逆删除、覆盖生产数据、危险迁移
3. 新增付费资源、消耗额度、修改账单/费用策略
4. 需要新增权限、凭证、第三方访问授权
5. 任务文件未定义但实际已经超范围

一句话：**内部能推进的，自己推进；外部会出事的，再来问。**

---

## 6. 文件归属与互不踩踏规则

### 6.1 后端 Agent 边界
- 主要改：`apps/api/**`、`packages/schema/**`、必要的后端测试与脚本
- 不自行改前端页面业务逻辑

### 6.2 前端 Agent 边界
- 主要改：`apps/web/**`、必要的前端测试与共享 UI
- 不自行发明接口字段
- 不把页面 fetch 逻辑散落在组件里

### 6.3 API Steward / Domain Model 边界
- 主要改：协议、DDL、DTO、共享 schema、契约文档
- 不直接把业务实现做成黑箱而无人知晓

### 6.4 QA / Migration 边界
- 主要改：测试、脚本、校验报告、验收文档
- 若修业务代码，必须补“为何越界”和回归结果

---

## 7. 合并前检查

每个分支准备合回 `main` 前，至少做这些检查：

- [ ] 已 rebase / merge 最新 `main`
- [ ] lint 通过
- [ ] typecheck 通过
- [ ] 本任务相关测试通过
- [ ] 对应文档已同步（如果涉及 DDL / OpenAPI / 页面行为）
- [ ] handoff 信息已写
- [ ] 未误带无关文件、临时文件、个人配置

---

## 8. 冲突处理规则

### 8.1 字段冲突
- DDL 与 OpenAPI 冲突时，先停在契约层解决
- 不允许前端先“凑活兼容两个字段名”长期存在

### 8.2 同文件冲突
优先级按“谁是该文件主责 Agent”判断：
- `apps/api/src/modules/homework/**` → Backend Biz 主责
- `apps/web/src/features/homework/**` → Frontend Biz 主责
- `docs/growthpilot/07_OpenAPI.yaml` → API Steward 主责
- `docs/growthpilot/05_数据库DDL.sql` → Domain Model 主责

### 8.3 时间冲突
如果两个 Agent 同时需要同一块文件：
1. 先拆文件边界
2. 拆不了就按 task 先后顺序排队
3. 实在冲突，就由主协调合并决策

---

## 9. Handoff 交接规范

每次交接必须写清楚：

```yaml
agent: A6
task_id: T-H1-3
branch: agent/A6/T-H1-3
changed_files:
  - apps/api/src/modules/homework/**
output:
  - analysis adapter
  - ai result persistence
checks:
  - lint pass
  - unit test pass
risks:
  - provider adapter still mock
next_handoff_to:
  - A9
  - A10
```

### 9.1 不合格交接的典型表现
- 只说“我做完了”，不说改了哪些文件
- 不说依赖和风险
- 不说下一棒给谁
- 改了契约但不通知前后端

这种交接，等于没交接。

---

## 10. 推荐合并节奏

### Wave 内节奏
- 每个 Agent 分支小步推进
- 每完成一个任务卡，尽快合流到 `int/wave-x` 或直接回 `main`
- 不要让一个分支活太久

### 每日节奏
- 早上：拉最新 `main`
- 开发中：按任务卡推进
- 收工前：提交、推送、写 handoff

### Wave 收口
- 先过模块级测试
- 再过主流程联调
- 再由 QA 统一回归
- 最后进入发布检查

---

## 11. 推荐 PR / 合并说明模板

```markdown
## Summary
- 完成了什么
- 对应哪些 WBS / task_id

## Changed Files
- 关键目录/文件

## Checks
- lint
- typecheck
- tests

## Risks / Follow-ups
- 尚未完成部分
- 下一棒交给谁
```

---

## 12. 禁止事项

以下行为一律算协作事故：

1. 在 `main` 直接堆未经验证的大改
2. 改 DDL / OpenAPI 不通知上下游
3. 把不同模块的无关改动揉进一个 commit
4. 把任务做成半截却不写风险说明
5. 用“先这样吧”掩盖字段漂移、状态机冲突、数据一致性问题
6. 把 task 文件当装饰品，不执行、不回写状态

---

## 13. 最终约束

一句话：

**本项目允许并行，不允许混乱；允许自动推进，不允许无痕乱改。**
