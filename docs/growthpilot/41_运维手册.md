> 覆盖范围：`QA-34`

## 1. 服务架构

```text
Internet
  -> DNS
  -> Edge TLS (host nginx or cloud LB)
  -> Compose nginx
     -> Web (Next.js on :3001)
     -> API (NestJS on :3000)
        -> PostgreSQL
        -> Redis
        -> local object storage or S3-compatible storage
```

关键说明：
- 当前仓库默认是单域名同域代理，`/api` 走同一个入口
- 健康检查统一看 `/health` 与 `/health/ready`
- API 结构化日志默认输出 JSON 到 stdout/stderr
- 迁移、部署、备份、回滚都必须写操作日志到 `/var/log/growthpilot`

## 2. 服务启停命令

### 2.1 Docker Compose 方式

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml ps
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d
docker compose --env-file .env.prod -f docker-compose.prod.yml restart api
docker compose --env-file .env.prod -f docker-compose.prod.yml restart web
docker compose --env-file .env.prod -f docker-compose.prod.yml down
```

### 2.2 单服务查看

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml logs api --tail 200
docker compose --env-file .env.prod -f docker-compose.prod.yml logs web --tail 200
docker compose --env-file .env.prod -f docker-compose.prod.yml logs nginx --tail 200
docker compose --env-file .env.prod -f docker-compose.prod.yml logs postgres --tail 200
docker compose --env-file .env.prod -f docker-compose.prod.yml logs redis --tail 200
```

### 2.3 首次部署与重复发布的区别

- 首次部署：用 `docker compose ... up -d --build api web nginx`，因为当前 Compose 直接从本仓库 Dockerfile 构建应用。
- 重复发布：可在完成备份后运行 `bash deploy/scripts/deploy.sh`，但仍要确认构建物来源与当前发布策略一致。

## 3. 日志与观测

### 3.1 当前日志源

| 来源 | 获取方式 | 应重点关注的字段 |
|---|---|---|
| API request log | `docker compose logs api` | `requestId`、`method`、`path`、`status`、`durationMs` |
| API exception log | `docker compose logs api` | `code`、`requestId`、`status`、`details` |
| Nginx access/error | `docker compose logs nginx` | `status`、`request`、`remote_addr` |
| 发布/迁移/回滚 | `/var/log/growthpilot/*.log` | 完整终端输出、执行人、开始结束时间 |
| DB backup | `deploy/logs/db-backup.log` 或 `/var/log/growthpilot/db-backup.log` | 备份文件名、时间、是否成功 |

### 3.2 最小日志归档方案

部署资产已提供：
- `deploy/examples/growthpilot.logrotate.conf`

落地步骤：
1. `sudo mkdir -p /var/log/growthpilot`
2. `sudo install -m 0644 deploy/examples/growthpilot.logrotate.conf /etc/logrotate.d/growthpilot`
3. 所有发布命令都用 `tee -a /var/log/growthpilot/<action>.log`

命令模板：

```bash
DEPLOY_ENV_FILE=.env.prod npm run db:migrate -- --mode compose-run 2>&1 | tee -a /var/log/growthpilot/migrate.log
DEPLOY_ENV_FILE=.env.prod npm run db:seed -- --mode compose-run 2>&1 | tee -a /var/log/growthpilot/seed.log
DEPLOY_ENV_FILE=.env.prod bash deploy/scripts/deploy.sh 2>&1 | tee -a /var/log/growthpilot/deploy.log
DEPLOY_ENV_FILE=.env.prod bash deploy/scripts/rollback.sh 2>&1 | tee -a /var/log/growthpilot/rollback.log
```

### 3.3 发布日常用排查命令

```bash
curl -fsS https://app.example.com/health | jq
curl -fsS https://app.example.com/health/ready | jq
docker compose --env-file .env.prod -f docker-compose.prod.yml ps
docker compose --env-file .env.prod -f docker-compose.prod.yml logs api --since 10m
docker compose --env-file .env.prod -f docker-compose.prod.yml logs nginx --since 10m
df -h
free -m
docker stats --no-stream
```

优先顺序：
1. `docker compose logs`
2. `/var/log/growthpilot/*.log`
3. 外部日志系统 / 云监控（如有）

排查时至少抓取：
- 报错时间窗口前后 10 分钟
- 对应 `requestId`
- 相关用户、批次、文件名、路由

## 4. 监控与告警

### 4.1 最低告警面

| 项目 | 检查方式 | 阈值 |
|---|---|---|
| `/health` | 外部 uptime | 连续 3 次失败 |
| `/health/ready` | 外部 uptime 或内部定时 curl | 任一子项为 `error` |
| 磁盘 | 主机监控 | `> 80%` |
| DB 连接数 | PostgreSQL 监控或 SQL | 达到池上限 `80%` |
| API 5xx | Nginx 日志 / 网关监控 | 持续 10 分钟高于基线 |

### 4.2 推荐人工巡检命令

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml exec -T postgres \
  sh -lc 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select count(*) as active_connections from pg_stat_activity where datname = current_database();"'
```

```bash
curl -fsS https://app.example.com/health/ready | jq '.checks'
```

## 5. 常见问题排查

### 5.1 首页无法打开

检查：
- 主机侧 TLS/Nginx 或云 LB 是否存活
- Compose 内 `nginx` 与 `web` 是否 healthy
- DNS 是否已正确指向
- 若用了主机侧 TLS，确认 `NGINX_PORT` 是否与 edge 配置一致

### 5.2 登录失败

检查：
- `JWT_SECRET` 与 API 实例是否一致，且没有使用占位值
- `/auth/login` 是否返回 200/401
- 浏览器 cookie / token 是否正确写入
- `CORS_ORIGIN` 与 `CORS_ORIGINS` 是否一致

### 5.3 `/health/ready` 失败

检查：
- 返回体中 `db` / `redis` / `storage` 哪一项为 `error`
- `DATABASE_URL` / `REDIS_URL` / `OBJECT_STORAGE_DRIVER` 是否与当前部署方案一致
- 本地磁盘是否写满，导致 `storage` 检查失败

### 5.4 学生列表为空

检查：
- 迁移批次是否执行成功
- 数据库连接是否正常
- 当前账号是否有校区数据权限

### 5.5 文件上传失败

检查：
- `OBJECT_STORAGE_DRIVER` 当前值
- 如为 `local`，确认 `apps/api/.data/object-storage` 可写
- 如为 `s3`，确认 `S3_*` 环境变量和 bucket 权限
- 反向代理 `client_max_body_size`

### 5.6 数据库连接异常

检查：
- `DATABASE_URL`
- DB 连接池占用
- 最近是否刚执行 migration 或大批量导入
- 托管库或 Compose 内库是否触发连接数上限

## 6. 备份与恢复

### 6.1 备份最低要求

- 数据库全量备份：每天至少一次
- 对象存储关键前缀快照：每天至少一次
- `.env.prod` 与反向代理配置变更前必须备份

### 6.2 常用命令

```bash
DEPLOY_ENV_FILE=.env.prod npm run db:backup
DEPLOY_ENV_FILE=.env.prod npm run db:restore -- --input deploy/backups/postgres/<backup-file>.sql.gz
DEPLOY_ENV_FILE=.env.prod bash deploy/scripts/rollback.sh
```

### 6.3 恢复流程

1. 确认恢复范围：应用、数据库、对象存储、配置
2. 停止写流量
3. 恢复数据库
4. 恢复对象存储
5. 回滚应用
6. 执行冒烟验证
